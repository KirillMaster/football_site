# Research: Полноценный редактор новостей в админке

## R1. Сохранение галерей и видео в tiptap без потерь

**Decision**: Ввести три кастомные ноды поверх существующих зависимостей tiptap:
`newsImage` (figure с `<img alt>`), `newsGallery` (контейнер-грид, содержащий `newsImage`),
`newsVideo` (atom-нода `<div><video><source></video></div>`). У каждой — `parseHTML`, распознающий
разметку эталонных новостей, и `renderHTML`, выдающий её же байт-в-байт по структуре (inline-стили,
`loading="lazy"`, `controls preload="metadata" playsinline`).

**Rationale**: Публичная страница рендерит `contentRu` через `dangerouslySetInnerHTML` в `prose-club`
без собственных стилей для галереи — разметка обязана быть самодостаточной. StarterKit молча
выбрасывает всё, для чего нет схемы ноды; именно поэтому вставленные вручную галереи исчезали при
`getHTML()`. Симметричная пара `parseHTML`/`renderHTML` также решает FR-020 (открытие программно
созданных новостей без потерь).

**Alternatives considered**:
- Хранить контент как HTML-строку в textarea без WYSIWYG — отбрасывает ценность редактора, админ
  не сможет работать с разметкой.
- Расширение `allowedTags` через generic HTML-ноду — tiptap не даёт надёжного round-trip для
  произвольного HTML, порядок атрибутов и стили теряются.
- `@tiptap/extension-image` как есть — даёт `<img>` без figure/alt-редактирования и без грида.

## R2. Эндпоинт загрузки медиа новостей

**Decision**: Отдельный `POST /api/admin/news/media` (роль admin), использующий существующий
`IStorageService`: сохраняет файл в S3, регистрирует `MediaFile` с типом, выведенным из
content-type (Image/Video), и возвращает `{ url, key, type }`. Записи `Photo` не создаёт.

**Rationale**: Действующий `POST /api/admin/photos/upload` жёстко ставит `MediaFileType.Image`
и создаёт `Photo`, из-за чего каждая иллюстрация новости попадала бы в публичную фотогалерею
(FR-016). Менять поведение существующего эндпоинта нельзя — на нём держится раздел фотогалереи
(FR-019). Отдельный маршрут разделяет два сценария и позволяет расширить список допустимых
content-type видеоформатом без риска для галереи.

**Alternatives considered**:
- Флаг `?skipGallery=true` на существующем эндпоинте — скрытая смена семантики одного маршрута,
  легко забыть на вызывающей стороне.
- Пометка `Photo.IsHidden` и фильтрация в публичном запросе — создаёт мусорные строки в БД и
  требует правки публичных запросов галереи.

## R3. Обложка при создании новости

**Decision**: Добавить `CoverImage` (nullable) в `CreateNewsCommand`, прокинуть его в
`News.Create(...)` через уже существующий доменный метод `SetCoverImage` сразу после создания;
валидатор — необязательное поле, при непустом значении проверка максимальной длины URL.

**Rationale**: Домен уже умеет хранить и менять обложку (`News.CoverImage`, `SetCoverImage`);
единственный разрыв — команда создания её не принимает, поэтому обложку можно было задать только
вторым шагом через Update. Миграции не требуются.

**Alternatives considered**:
- Двухшаговое создание на фронте (create → сразу update) — гонка и лишний запрос, при сбое второго
  шага новость остаётся без обложки.

## R4. Ввод alt-текста

**Decision**: Alt редактируется инлайн — подпись под изображением внутри ноды (contenteditable
атрибут ноды), с предзаполнением из имени файла и видимой пометкой у изображений без alt.

**Rationale**: Модальное окно на каждый файл при загрузке галереи из 3-10 фото превращает вставку
в серию диалогов; инлайн-правка позволяет загрузить всю галерею одной операцией (FR-005) и заполнить
описания потом. Пометка «без описания» делает SEO-пробел заметным без блокировки сохранения.

**Alternatives considered**:
- Обязательный alt перед сохранением — блокирует срочную публикацию, спека не требует.
- Диалог по каждому файлу при загрузке — конфликтует с мульти-выбором.

## R5. Уникальность и формат slug

**Decision**: Автогенерация из заголовка (существующий транслит + суффикс времени), ручная правка,
клиентская проверка `^[a-z0-9-]+$` перед отправкой; серверная — существующий валидатор
`CreateNewsCommand.Slug`. Конфликт занятого slug распознаётся по ответу сервера и показывается
как понятное сообщение (EC-4).

**Rationale**: Формат и уникальность уже обеспечены на сервере (валидатор + уникальный индекс);
клиенту остаётся не отправлять заведомо некорректное значение и внятно показать отказ.

**Alternatives considered**:
- Предварительная проверка занятости отдельным запросом — лишний round-trip, всё равно не снимает
  гонку, ответ сервера остаётся источником истины.

## R6. Видео

**Decision**: Принимать только `video/mp4`, без серверной перекодировки и без генерации постера;
`preload="metadata"`, чтобы страница новости не тянула видеофайл целиком.

**Rationale**: VPS ~1 ГБ RAM, ffmpeg-перекодировка на нём недопустима (A-2); mp4/H.264 воспроизводится
во всех целевых браузерах; эталонные новости используют ровно такую разметку.

**Alternatives considered**:
- Загрузка видео на внешний хостинг с встраиванием плеера — внешняя зависимость и другой визуальный
  язык страницы.
- Серверная перекодировка — не проходит по ресурсам VPS.

## R7. Защита от затирания полей при редактировании

**Decision**: `openEdit` загружает полную новость (`getAdminNewsById`) и заполняет ВСЕ поля формы,
включая обложку, теги, slug, meta и статус; сохранение отправляет состояние формы целиком.

**Rationale**: FR-004/FR-015 нарушаются именно тогда, когда часть полей не попала в форму и уходит
пустой/дефолтной. Полная загрузка + полная отправка исключает класс ошибки без частичных PATCH.

**Alternatives considered**:
- PATCH только изменённых полей — потребовал бы нового серверного контракта ради той же гарантии.
